# Phase 1: Neon persistence

Only presets and saved bulk analysis move to PostgreSQL. WCA history continues
using the existing MySQL implementation and will remain unavailable on Vercel
until a later phase. OAuth, URLs, preset ownership, and the frontend are unchanged.

## 1. Create the database

In Neon create a project named `rubiks-cube-blind-tracer`, a production branch
named `production`, and a database named `tracer`. Use a region near your Vercel
function region. Use the PostgreSQL role created by Neon for the initial setup.
No WCA tables or WCA results import are needed for this phase.

Copy two connection strings for **the same branch, database, and role**:

- Pooled connection: runtime `DATABASE_URL`.
- Direct connection: migration `DATABASE_URL_DIRECT`.

Keep the TLS parameters supplied by Neon. Both URLs contain credentials and
must stay out of source, screenshots, logs, and commits. Provision a separate
branch/database for development and previews.

## 2. Install and configure

From the repository root, with your Python virtual environment active:

```sh
python -m pip install -r requirements.txt
```

In Vercel Project Settings → Environment Variables, add `DATABASE_URL` using the
pooled connection URL, scoped to Production. Keep the existing `FLASK_SECRET_KEY`,
`WCA_CLIENT_ID`, `WCA_CLIENT_SECRET`, and `WCA_REDIRECT_URI` unchanged. No
`PRESET_DATABASE` or `BULK_DATABASE` file path is needed in production.

`DATABASE_URL_DIRECT` is for your local migration shell or trusted migration job;
it is not needed by the running Vercel app. Configure Preview with a separate
pooled URL if you deploy previews. Vercel deployments without `DATABASE_URL` will
refuse to fall back to SQLite. For other production hosts, set
`APP_ENV=production` as well. `VERCEL=1`, production/preview `VERCEL_ENV`, and
`FLASK_ENV=production` also prevent SQLite fallback.

Load the direct URL into your local shell without putting it in shell history:

```sh
printf 'Paste Neon DIRECT connection URL (input hidden): '
stty -echo
IFS= read -r DATABASE_URL_DIRECT
stty echo
printf '\n'
export DATABASE_URL_DIRECT
```

This shell input is not saved to a file. The app and migration tool do not
automatically load `.env` files.

## 3. Initialize the schema

```sh
python scripts/persistent_data.py init
```

This applies `migrations/001_persistent_features.sql` in a transaction and records
its filename and checksum in `app_schema_migrations`. It is safe to rerun;
changed previously applied migrations are rejected. PostgreSQL tables are never
created during web requests. Run initialization against an empty database/schema;
pre-existing unmanaged tables are deliberately not silently adopted.

The three tables retain serialized JSON as `TEXT`. Preset IDs are generated by a
PostgreSQL identity sequence; imported IDs and batch IDs are preserved.

## 4. Import SQLite data

Stop local writes while backing up/importing. Back up both SQLite databases using
SQLite's backup command (which also handles databases using WAL):

```sh
mkdir -p /tmp/tracer-phase1-backup
sqlite3 instance/presets.sqlite3 '.backup /tmp/tracer-phase1-backup/presets.sqlite3'
sqlite3 instance/bulk.sqlite3 '.backup /tmp/tracer-phase1-backup/bulk.sqlite3'
python scripts/persistent_data.py import-sqlite \
  --presets /tmp/tracer-phase1-backup/presets.sqlite3 \
  --bulk /tmp/tracer-phase1-backup/bulk.sqlite3
```

Use your actual local paths if you configured `PRESET_DATABASE` or `BULK_DATABASE`.
Retain backups somewhere durable before changing or retiring your local setup.
If you intentionally have no existing data, initialization alone is sufficient;
do not create empty placeholder files and pass them to the importer.

The importer reads SQLite in read-only mode and imports all three tables in one
PostgreSQL transaction. Identical existing rows are accepted on reruns; conflicting
IDs or preset names abort the import rather than overwrite data. It verifies every
source field against PostgreSQL and resets the preset sequence above the highest
imported ID. It takes write-blocking table locks during import, so run it before
sending production traffic to the database. Saved `/bulk/<id>` URLs remain valid.

## 5. Verify before deployment

While the destination is still quiet, run:

```sh
python scripts/persistent_data.py verify-sqlite \
  --presets /tmp/tracer-phase1-backup/presets.sqlite3 \
  --bulk /tmp/tracer-phase1-backup/bulk.sqlite3
```

Verification is read-only. It compares every source row and exact table counts;
extra destination rows cause a failure, so run this before creating new presets
or batches during smoke testing.

Run the existing SQLite tests with `DATABASE_URL` unset. Integration tests require
a **separate test database/branch**, supplied through `TEST_DATABASE_URL` (direct
connection URL). They create and remove only random `test_persistence_*` schemas:

```sh
unset DATABASE_URL
python -m unittest discover -s tests
# Securely load the separate test database's URL into TEST_DATABASE_URL first.
python -m unittest discover -s tests -p 'test_postgres_persistence.py'
```

The PostgreSQL test file skips when `TEST_DATABASE_URL` is absent. The existing
suite currently has an unrelated batch-limit test expecting 1,000 while the app
allows 10,000; this migration does not change that behavior.

For an application smoke test, securely load the pooled Neon URL into
`DATABASE_URL` and start `python app.py` locally. Keep the local OAuth redirect
and stable local secret configured. Sign in, then:

1. Confirm preset listing returns JSON; save and reload a preset after restart.
2. Confirm duplicate names still return 409 and another user cannot see it.
3. Open an imported `/bulk/<id>` URL; test filters, sorting, and error rows.
4. Save a new bulk batch and reopen its URL after restart.
5. Confirm database failures produce a JSON 503 from the preset API.

Only then redeploy Vercel with its pooled `DATABASE_URL`. Keep the SQLite backups
for rollback. Once PostgreSQL accepts new writes, switching back to SQLite alone
would omit those writes; reconcile them before any rollback.

Local development without `DATABASE_URL` keeps the original SQLite behavior.
No credentials are needed for that fallback. No WCA MySQL changes are included.
